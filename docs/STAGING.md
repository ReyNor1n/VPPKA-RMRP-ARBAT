# Тестовая версия сайта

Боевой сайт — ветка `main`, GitHub Pages, каталог `/`, домен `vppka-arbat-rmrp.ru` (файл `CNAME`). Его настройки Pages, ветку деплоя и CNAME не переключать.

Тест — это отдельная сборка тех же исходников, а не вторая копия сайта и не параметр в адресе. Команда `node tools/build-staging.mjs` складывает её в `dist-staging/` (в git не входит).

## Что работает

В `app.js` у `route()` одна проверка: если задана `window.__VPPKA_STAGING_PATCH`, она вызывается. На боевом сайте этой функции нет, вид и поведение не меняются. В тестовой сборке она подменяет вход, заявки и заголовок вкладки.

Страницы, вёрстка и шрифты те же. Состав, новости и контакты — демонстрационные: вымышленные ФИО, без фотографий людей, без Discord и без боевых идентификаторов. Сверху постоянная плашка **ТЕСТОВАЯ ВЕРСИЯ**.

## Что выключено

- Firebase Auth, Firestore, Storage и Cloud Messaging боевого проекта `vppca-rmrp`. Демо-сборка вообще не вызывает Firebase (`PASTE_` в конфиге).
- Discord: OAuth, код в личные сообщения, роли, сообщения бота, вебхуки, приглашение на боевой сервер.
- Заявки, ключи, чат, пуши, скачивание боевых APK и Windows-установщика.
- Service worker с именем кэша `vppka-staging-…`. Он удаляет только свои старые кэши. Кэши `vppka-v…`, `vppka-banners` и `vppka-music` не трогает. На боевом домене этот worker снимает себя и ничего не стирает.
- `localStorage`, `sessionStorage`, IndexedDB и Cache Storage страницы пишутся с префиксом `vppka-staging`, чтобы при случайном открытии на том же origin не затереть боевой вход.

Проверка: `node --test tools/test/staging-isolation.test.js`.

## Как выкатывать нововведение в тест

1. Ветка от `main`. Правки — в общих файлах (`index.html`, `app.js`, `style.css` и остальных), не в отдельной копии сайта.
2. `node --test tools/test/staging-isolation.test.js`
3. `node tools/build-staging.mjs`
4. Локально из каталога сборки: `python3 -m http.server 8090` и открыть `http://127.0.0.1:8090/`. Файл с диска (`file://`) не подходит: не загрузятся данные и service worker.
5. На pull request workflow «Тестовая сборка» собирает тот же каталог и кладёт его в артефакт Actions `vppka-staging`. Это архив, не сайт. Workflow не публикует GitHub Pages и не меняет боевой домен.

Публичного адреса у теста сейчас нет: у репозитория один GitHub Pages, и он занят боевым сайтом. Подменять источник Pages, ветку `main` или `CNAME` нельзя — домен начнёт отдавать тест или отвалится.

## Как перенести одобренное в прод

Только после слова владельца «Публикуй».

1. В `main` сливается ветка с исходниками, не каталог `dist-staging/`.
2. GitHub Pages сам публикует `main` на `vppka-arbat-rmrp.ru`.
3. Дальше, как и раньше: `node tools/publish-version.mjs`, если нужно сразу обновить уже открытые вкладки.

Пока этого слова нет, в `main` тест не вливать и на боевой домен не выкладывать.

## Отдельный backend, если демо-данных мало

Это делает владелец. Платные ресурсы не нужны, боевой проект и правила Firestore не менять, DNS Cloudflare не трогать.

1. Новый проект Firebase на бесплатном плане Spark. Идентификатор проекта — любой, кроме `vppca-rmrp`. Правила скопировать в новый проект и опубликовать там. Боевые правила не ослаблять и не переиздавать.
2. Отдельное приложение Discord и отдельный бот. Redirect URI — адрес теста, не `https://vppka-arbat-rmrp.ru/`. Боевое приложение не дополнять тестовым redirect: тот же бот пишет в боевой сервер и выдаёт боевые роли.
3. Хостинг на другом origin, без смены DNS и без смены Pages этого репозитория. Бесплатные варианты: сайт `*.pages.dev` у Cloudflare Pages (зону DNS не редактировать), Hosting нового проекта Firebase или Netlify/Surge. Не `reynor1n.github.io` и не боевой домен: сборка на этих хостах отказывается запускаться.
4. Локальный файл `tools/staging/backend.local.json` (в git не класть):

```json
{
  "firebaseConfig": {
    "apiKey": "",
    "authDomain": "",
    "projectId": "",
    "storageBucket": "",
    "messagingSenderId": "",
    "appId": ""
  },
  "appCheckSiteKey": "",
  "discordOAuth": { "clientId": "", "redirect": "" }
}
```

5. `node tools/build-staging.mjs --backend tools/staging/backend.local.json`

Сборка останавливается, если в файле боевой проект, ключ, домен или приглашение Discord. Даже в этом режиме адрес с `vppca-rmrp`, боевым ключом или боевым Discord-приложением блокируется, пуши в FCM не отправляются, запросы к `discord.com/api` и вебхукам — тоже. Пока файла нет, сайт остаётся на демонстрационных данных.
